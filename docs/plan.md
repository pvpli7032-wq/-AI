## 1. 先说结论

SkaFull/cps 可以继续当基座，但它的价值比上一版说的小。**能复用的是壳（若依后台、小程序骨架、联盟 SDK 封装），业务主线基本没有。**

上一版有三处说错了，这里更正：

| 上一版的说法 | 核对后的事实 |
|---|---|
| 转链能直接用 | 转链能调通，但**不带用户身份**，订单回来分不清是谁的。淘宝算了代理信息却没用上（`MiniappTbkController.java:664-701`），京东的推广位由客户端传入，拼多多用全局推广位（`PddApiServiceImpl.java:90,164`），大淘客转链失败时静默返回不带 pid 的口令（`DtkApiServiceImpl.java:367-393`） |
| 联盟 SDK 能直接用 | 淘宝、京东、拼多多三家的官方 SDK jar 都不在仓库里，`pom.xml` 注释写着「请根据自己的进行申请」。要自己下载补齐才能编译 |
| 技术栈是 Spring Boot 2.x | 实际是 Java 21、Spring Boot 4.0.3、若依 3.9.1、Vue 2 + Element UI |

还有一条比上面都重要：**用户粘贴链接后解析出商品的功能，基座没有。** 它现在的路径是「用户在小程序里搜商品 → 看详情 → 拿口令」，不是你们要的「粘贴链接 → 查佣金 → 给链接」。你们最核心的入口要新做。

## 3. 业务主流程

```
用户粘贴链接或口令
  → 解析：识别平台和商品 ID
  → 查佣金：有佣金则继续，无佣金返回提示
  → 算展示金额：按规则算「预计返利」
  → 转链：带上这个用户的归因标识
  → 记录一条查券记录
  → 用户复制口令或跳转，到平台下单
  ……
定时同步联盟订单
  → 存原始数据
  → 归因：这单是谁的
  → 下单：生成预估返利（用户可见，不进余额）
  → 确认收货：进入冻结，开始计 N 天
  → N 天到期：进入可提现余额
  → 用户申请提现 → 审核 → 第三方商户打款
  ……
联盟后续变化（退款、维权、处罚、结算差额）
  → 回退或调整对应的返利、邀请奖励、补贴
  → 余额不够扣就形成负余额，未结清不能提现
  ……
定期对账：联盟报表、联盟到账、系统台账、打款记录四边核对
```

## 4. 商业逻辑

### 4.1 链接解析

| 平台 | 输入形态 | 处理 |
|---|---|---|
| 淘宝 | 淘口令、短链、商品链接 | 解析出商品 ID。基座已有大淘客 `DtkParseTaokoulingRequest`、`DtkParseContentRequest`，优先接这两个；需确认全局大淘客 key 能否调用 【待核】。淘宝商品 ID 有旧数字 ID 和新长 ID 两种，要归一化后再比对（速推客 138） |
| 京东 | 短链、商品链接 | 解析出 skuId，基座有 `jd.union.open.goods.bigfield.query` 等查详情接口 【已核】 |
| 拼多多 | 商品链接、短链 | 解析出 goods_sign 或商品 ID 【待核】 |

规则：
- 用户主动粘贴后才处理，不自动读剪贴板（规避微信 2.5.15/2.5.20 相关风险）
- 解析失败、商品无佣金、佣金过低，分别给不同提示，并记录。这三个数据决定「查券失败率」，是转化诊断的关键
- 按平台加限流，同一用户短时间内重复查同一商品直接走缓存；基座只有接口级限流，要加按用户限流
- 淘宝标题搜索入口：输入内容长度像商品标题时按标题查（速推客 140 写 54～64 字符触发，第一版可选）
- 无佣金时给同款推荐回落（速推客 141），提示文案后台设置
- 查券结果展示：约返、券、券后价、划线价、复制口令。所有人能看佣金的详情页要改成只显示预计返利
- 拼多多比价订单佣金为 0（速推客 148）：用户先在拼多多看过商品再查券就没佣金，提示文案和是否提示后台设置

### 4.2 归因：这单是谁的

这是整个系统最容易出错的地方。订单绑错，钱就发错。

**三个平台的标识方式：**

| 平台 | 方式 | 确定性 |
|---|---|---|
| 京东 | 转链带 subUnionId，订单回传 【待核：权限要申请】 | 高 |
| 拼多多 | 转链带 custom_parameters，需备案；订单响应带回自定义参数 【已核：接口存在，细节待核】 | 高 |
| 淘宝 | 见下方 | 分情况 |

**淘宝的处理（同行做法）：**

追踪 PID 的原理是「多个 pid 轮换使用，根据 pid + 商品 id + 用户 id 实现自动绑定」，同行要求至少 50 个，查券后 48 小时内有效。【已核：速推客】

系统要这样设计：
- 建 PID 池。用户查券时，给他分一个「这个商品当前没被别人占用」的 PID，记录 pid + 商品 + 用户 + 过期时间
- 占用 48 小时。这个窗口内该 PID 下这个商品的订单都归他，分享给别人下的单也归他
- 默认 PID 不能放进追踪池。PID 用完时用默认 PID 兜底，这类订单进无主订单池，否则会绑错 【已核：速推客原文】
- 推广位上限 200 个，留 1 个做默认 PID，其余进追踪池。同一商品 48 小时内最多约 199 人能拿到专属绑定，超出的进无主订单池
- 池子要监控单品占用率。占用时长做成后台可配，爆款可以缩短占用时间，把名额转得快一些

商品 ID 匹配是更弱的兜底：同行默认 1 小时，最长 24 小时，查过这个商品的用户在窗口内出单就绑给他。多人查同一商品时不自动绑，要用户手动提交订单号。【已核：速推客】系统里这类订单先进无主订单池等认领。

**归因优先级：**

同行顺序是「订单尾号 > 手动提交待绑定 > 追踪 PID > 代理 PID > 商品 ID」。【已核：速推客 152】小程序不做尾号（2026-03 起尾号不固定）和代理 PID。【建议】优先级：

1. 平台确定标识（subUnionId、custom_parameters、relation_id）
2. 用户手动提交订单号
3. 追踪 PID + 商品 ID
4. 商品 ID 匹配
5. 进无主订单池

规则：
- 每次归因记录方式、置信度、决策人、时间，只追加不覆盖
- 高优先级可以改判低优先级，反过来不行；已入账的单改判要走人工并审计
- 两个人提交同一订单号：不自动判，转人工
- 淘宝 relation_id 需要用户做淘宝授权，小程序里转化差，【建议】第一版不做，保留字段

**从速推客补进来的归因规则：**【已核：速推客 037、044、167、168】
- 追踪 PID 同行最少 50 个、48 小时、随机分配，淘宝总 PID 不超过 200，京东不超过 500。部分截图仍写 100 个，167 正文写明「之前是100个，现在改为50了」，以 50 为准
- 用了别人红包或礼金的单不会进我方联盟，不是无主订单，不要在无主池里找。我方自建红包用的 PID 也会回单，要登记成独立类型区分
- 配置屏蔽 PID：其他业务用的 PID 下的单不让用户认领（165）
- 租约只对租约开始后的订单生效，防止回溯绑走旧单（【建议】，从 165 的风险推出）
- 手动提交失败要给具体原因：未找到、别人已绑定、自己已绑定、屏蔽 PID、失效状态、超出时间。订单号展示时打码
- 漏斗单列「绑不上」的原因，这是归因质量的主要指标
- 换联盟账号时旧账号保留授权，继续同步在途订单状态（014）
- 下单后提示「N 分钟内没收到绑定提醒，就提交订单号」。同行资料写 2/3 分钟不统一，N 做成配置
- 提示要包含：不要用购物红包、购物车和收藏里的旧商品要先删、绑定后取消或维权会失效（144-10、143-01、034-05 中间页截图）
- 转发卡片不得携带发卡人身份，打开的人看到的是自己的数据（035），加入验收

京东 PID 同行用「会员 ID + 手机后 7 位」（153），和本方案 4.2 的 subUnionId 不同，同行资料未说明如何绕开 500 上限，开工前核实。

### 4.3 钱怎么算

**基本公式：**

```
净佣金 = 联盟佣金 × (1 - 平台服务费率)
用户返利 = 净佣金 × 用户比例
邀请提成 = 用户返利 × 提成比例            （按用户返利算，不按联盟佣金）
补贴 = 新人、前几单、下单数量等活动的奖励
平台毛利 = 净佣金 - 用户返利 - 邀请提成 - 补贴 - 打款和税务成本
```

**示例（数字仅作演示）：** 商品 100 元，佣金 20 元，服务费 10%，用户比例 50%，提成 20%，打款税务成本按发放额 8% 计：

| 项目 | 金额 |
|---|---|
| 净佣金 | 18.00 |
| 用户返利 | 9.00 |
| 邀请提成 | 1.80 |
| 打款税务成本 | 0.864 |
| 平台毛利 | 6.336 |

`净佣金` 公式和提成算法来自同行资料。【已核】实际服务费率、灵工成本待核。京东非自营商品同行扣 10% 佣金（153），净佣金计算要留这一项。

**比例模式：** 基座现有写死的「估算佣金 × 40%」，改为按单笔佣金分档，档位后台可配。同行默认档 `1:60|3:55|7:50|10:45|20:40|30:35|100:30|1000:25`（158-02 截图已核，含义是佣金越高比例越低），每档可配「亏损不能大于 Z」。比例填 0 不能被系统当成「未设置」（同行有这个坑，164）。档位的默认值由公司在上线前填，公开仓库不写真实比例。

**舍入规则：** 用户金额四舍五入到分（`HALF_UP`），所有计算走同一个方法，基座的 double 工具 `Arith` 不能用于金额。四舍五入可能让多项之和略超净佣金，最差毛利校验按舍入后的金额算。低于 0.01 时按后台配置补 0.01 或指定金额（同行做法，这部分会亏，要计入毛利）。

**预估和实际：** 下单时用预估佣金展示，用实际佣金结算。金额以联盟返回的订单行实际佣金为准重算，比例用下单时锁定的规则版本。实际佣金必须有上限校验，基座现在没有（风险 5）。

**结算口径开关：** 「按结算佣金计算」「淘宝已收货视为结算」两项同行做成开关（152、043），对应第 4.5 节确认收货和结算是否同一时点的问题，抖音 15 天、唯品会 N 天的延迟不在第一版范围。预售订单定金阶段归属不变，确认收货后才有佣金（043）。首购数据次日 9:00 后才可见（050）。

### 4.4 奖励规则

后台要能配的规则分两类，**比例规则互斥，奖励规则可叠加**。

**比例规则（一单只命中一条）：** 优先级从高到低

1. 定向：指定用户、商品、店铺、类目
2. 新人：前 N 单用更高比例
3. 阶梯：按累计有效单数或金额
4. 基础：按平台和类目

定向与阶梯组合：【建议】第一版做成开关，默认关闭，减少比例算不清的情况。同行的阶梯是多条件同时满足才算（045）；自购排除、「正常结算」是有效单候选口径。

**奖励规则（可叠加）：**

| 类型 | 配置项 | 触发时点 |
|---|---|---|
| 邀请提成 | 比例、适用平台、有效期 | 跟随被邀请人的返利 |
| 邀请首单奖 | 固定额 | 被邀请人首个有效单过冻结期 |
| 邀请前 N 单奖 | 每单固定额、N | 被邀请人每个有效单过冻结期 |
| 下单数量奖 | 累计 N 单、奖励额 | 第 N 个有效单过冻结期 |
| 前 N 单补贴 | 每单固定额或比例 | 随订单 |

**三条硬规则：**

1. **保存时校验最差毛利。** 把规则叠到最差情况算一遍，超过上限不准保存。比如用户比例 70% + 提成 30% + 补贴，可能吃掉全部净佣金
2. **规则有版本。** 改规则只影响之后的单，已下单的按快照走
3. **奖励发放看「有效单」，且过冻结期才发。** 不然下单就发，退货后要追回，追回不了的都是亏损

**不做：** 隐性差别定价（同行叫杀熟规则，011-05 截图有「佣金新用户杀熟模式」）。沉默 30 天回归用户的高返做成对用户可见的公开活动，不是隐性定价。

**提成由谁出：** 公司。同行开关「提成从用户扣除」不做，第 4.3 节公式不变。提成基数按用户返利算（163 算例 6.1）。

**新增规则（都受最差毛利校验约束，成本计入毛利）：**
- 首单强制返利：同行 0.1～0.5 元随机、5 天内（157），金额和时间后台可配，只发一次，自购刷单要防
- 邀请模式：比例随邀请数上升，同行到 70%（158-02 串 `5:35|10:40|…|200:70`）。和佣金分档互斥，每个用户只命中一种。邀请人数只算有效用户，否则可以刷到最高比例
- 沉默回归：沉默天数、前几单、比例后台可配

补贴低于 X 加 Y（166）不在这次决定里，第一版不做。

### 4.5 订单状态

**订单状态（来自联盟）：**

```
已付款 → 已收货 → 已结算
已付款 → 已结算（联盟直接给结算，或开启「淘宝已收货视为结算」）
已付款 → 失效
已收货 / 已结算 → 维权中 → 恢复原状态 / 部分退款 / 全额退款
已收货 / 已结算 → 部分退款 / 全额退款（联盟直接给退款结果，没经过维权中）
已收货 / 已结算 → 处罚（全部或部分）
```

第一次采到的订单从联盟给出的真实状态开始，不补造中间状态和时间。

各平台状态码映射表放在第 0 阶段填，三家状态含义不一样。特别要确认**确认收货**和**联盟结算**在各平台是否同一个时点。

**返利状态（我们自己的）：**

```
预估 → 冻结中 → 已入账
预估 → 作废
冻结中 ⇄ 暂停（维权期间，时钟不走）
冻结中 / 暂停 → 作废（冻结期内全额退款）
冻结中 / 暂停 → 部分追回（冻结期内部分退款）
部分追回 → 暂停 / 已入账 / 作废（只针对剩余仍冻结的部分）
已入账 → 部分追回 / 全部追回
部分追回 → 全部追回（只针对已入账的部分）
```

冻结期内的钱还没到用户手里，全额退款算作废，不算追回；已入账的才算追回。

规则：
- 状态只能按合法路径走。联盟数据乱序时，非法跳转记异常，不硬改
- 同一订单行重复同步不重复处理，用「平台 + 订单号 + 子订单号」做唯一键
- 冻结期 N 按平台配置，到期时间写在每条返利上
- 冻结按金额分档，档位后台可配：默认 ≥5/10/30/50/500 元分别冻 7/10/30/30/50 天，付款到收货不超过 24 小时冻 7 天，可按用户关闭（161-01 已亲核）。161 正文首档写 3 元，截图是 5 元，默认用截图值。低于首档资料没写，【建议】按首档天数
- 同行状态名：待收货、冻结中、已结算、已退款（181-02），用户端展示沿用这套，不展示内部状态码
- 付款到结算不足 24 小时的订单标为可疑（016，原文被截断，阈值后的动作未查到）
- 基座 `order_status` 取值前后不一致（`ruoyi-ui/src/views/system/commission/order/index.vue:113`），第 0 阶段映射表要覆盖

### 4.6 异常场景

这张表就是验收清单，每一行都要有测试用例。

| 场景 | 处理 |
|---|---|
| 冻结期内全额退款 | 返利、提成、补贴全部作废 |
| 冻结期内部分退款 | 按退款比例减少 |
| 入账后退款，余额够 | 从可用余额扣 |
| 入账后退款，余额不够 | 形成负余额，后续返利先抵，负余额未清不能提现 |
| 已提现后订单失效 | 同上 |
| 维权中 | 暂停计时，结果出来再走 |
| 淘宝部分处罚 | 按处罚比例回退返利、提成、补贴；保留人工导入处罚单入口（同行也靠导入） |
| 结算额和预估不同 | 按结算额重算，差额调账 |
| 被邀请人退款 | 邀请人的提成和奖励同步回退 |
| 下单数量奖发放后，计数的单退款 | 有效单数跌破门槛时回退奖励 |
| 手动提交晚于订单到达 | 无主订单改归属，补生成返利 |
| 无主订单到期没人认领 | 归平台，保留记录 |
| 改规则时有在途订单 | 按快照，不受影响 |
| 用户被封禁 | 冻结提现，余额保留待人工处理 |
| 拼多多比价订单 | 佣金 0，不算有效单，用户侧提示原因 |
| 订单被他人红包或礼金截走 | 不进我方联盟，不算无主；用户提交订单号时回「未找到」 |
| 联盟处罚冻结整月违规收入 | 计入垫付敞口，导入违规单后扣返利并通知用户（168-01） |
| 绑定失败或返利失效 | 通知用户，写明损失金额和新余额（036-01） |
| 上级或下级关系变更时的在途提成 | 保持原样：已下单的按下单时的关系快照，变更只影响之后的单 |

【建议】追回时：全部追回同时追回全部补贴，部分追回时补贴按相同比例。退款统计分开记 `refund_self`、`refund_promotion`，不混在一起（风险 16）。

### 4.7 账务设计

**原则：余额不是一个能直接改的数字，而是流水加出来的。** 落地在基座现有的 `sys_agent_commission_account`（已有 `balance`、`frozen_amount`、`withdrawn`）和 `sys_commission_flow` 上，在 `updateUserAccount` 基础上补幂等和并发控制。

**账户：**

| 账户 | 含义 |
|---|---|
| 用户冻结 | 收货后等待 N 天 |
| 用户可用 | 可提现，可以为负 |
| 用户提现中 | 已申请未打款 |
| 返利成本、奖励成本 | 平台支出 |
| 打款出账 | 钱实际付出去 |

**分录（每笔业务一借一贷）：**

| 事件 | 借 | 贷 |
|---|---|---|
| 确认收货 | 返利成本 | 用户冻结 |
| 冻结到期 | 用户冻结 | 用户可用 |
| 冻结期追回 | 用户冻结 | 返利成本 |
| 入账后追回 | 用户可用 | 返利成本 |
| 申请提现 | 用户可用 | 用户提现中 |
| 打款成功 | 用户提现中 | 打款出账 |
| 打款失败 | 用户提现中 | 用户可用 |

规则：
- 只追加，不改不删，错了发冲正分录
- 用「业务类型 + 业务 ID + 账户」做唯一键，防重复记账
- 账户余额表只是缓存，随时能用流水重算验证
- 改余额时锁账户行（`FOR UPDATE` 或版本号）
- 下单时不记账，预估金额只存在返利明细里
- 基座 `settleOrder` 结算后直接进可用，没有冻结（风险 3），接新流程时必须走冻结
- `platform_amount`、`total_commission`、`agent_user_id` 现在没人赋值，结算时要写全，否则对账对不上
- 提现号不能用若依 `Seq`，要用能保证全局唯一的生成器

### 4.8 垫付敞口

你们的模式是用户先拿钱，联盟后结算，所以要盯这个数：

```
垫付敞口 = 已入账 + 已提现 中，联盟尚未到账的部分
```

后台看板每天算：
- 当前敞口、峰值、按平台拆分
- 敞口到达上限时，提现全部转人工审核
- 退款率突增时单独告警（比如某个平台某类目的退款率翻倍）
- 通道预付余额不足告警
- 联盟授权失效告警必选且不可关，10 分钟重复（016）。大促前检查授权，大促订单延迟时告知用户（043）

试营业的判定不能只看 GMV。**要等一批订单走完结算，才算得出这批用户的真实毛利。**

### 4.9 提现（只定规则，通道后接）

**系统内要做的：**
- 申请、审核、状态流转、失败退回
- **现有 `/miniapp/.../withdraw/apply` 假接口要接到真实提现单上**，路径保留，在这之前前端入口不开放（第 2.2 节）
- 分层审核同行有三层：默认金额线（0.1/5/10）、前 N 次（3）、分组门槛（金额、笔数、维权笔数、结算笔数、前 10 笔平均联盟佣金比，只计已结算，填 0 关闭）。【已核：速推客 181】本方案口径：任一门槛触发就转人工（公司决定）
- 负余额、封禁、敞口超限时不能提现
- 提现门槛同行可配：最低门槛（1/3）、最高门槛（2000）、每日次数（1/3/10）、固定日期（`10|20`）、每月上限（50/1000/500000）、整数提现、无收货订单禁提、实名阈值（单笔 100、月累计 1000，后果被截断未查到）。第一版全部做成配置
- 「已审核」不等于「已打款」，两个状态分开。通道模式以申请时为准，通道不可用时降级人工
- 通道限额（同行单笔 200、单日 50000、单日单用户 2000）和本地限额分层校验
- 用户首次收款需要确认时，状态机要加「待确认」和「超时」。同行红包 72 小时，超时资金去向资料未写，接通道时确认
- 收款姓名和账号必须同一人，后台能改绑并留审计；转账场景用佣金报酬类；审核时效 24 小时
- 首次行为奖励同行 0.3/0.8 自动到账，和本方案「过冻结期才发」冲突，本方案保留过冻结期
- 同行的提现手续费配置和重复打款规则：查了没找到

**通道接口：**

```
提交打款(提现单号, 金额, 收款人信息) → 通道单号
查询结果(提现单号) → 成功 / 失败 / 处理中
回调处理(通道通知) → 更新提现单
```

硬要求：**提现单号就是幂等号。** 结果不明时只能查询，不能换号重发，不然会重复打款。微信官方文档有相同要求，第三方通道通常也是，接入时确认。

第三方通道确定后要确认：收款人要提供什么信息（姓名、身份证、手机号）、是否需要用户确认、手续费、开票和个税由谁承担。这几项影响毛利模型。

### 4.10 邀请

- 只有一级，A 邀请 B，B 下单 A 拿奖励
- 绑定时机：【建议】新用户首次授权时绑定；已下过单的老用户不能再绑
- 一个人只能有一个邀请人，绑定后不能改（后台人工可改，留审计）。基座现有绑定有 replace-all 和改绑问题（风险 15），要收口
- 不能邀请自己，不做上下级链路。同行「奖励上上级」（196-13）是多级，明确不做
- 邀请码现在挂在 `sys_tbk_agent_apply`，被 `uk_mini_app_id` 卡成全小程序一条，普通用户的邀请码按第 9.1 节第 2 项放到 `sys_wechat_user`。该表现在没有邀请码字段，`SysWechatUserMapper.selectSysWechatUserByInvitationCode` 却在查，加字段时一起对齐
- 奖励看规则配置，过冻结期才发
- 防刷信号：同设备批量新号、被邀请人集中买同一低价商品、订单全部退款。命中后暂停奖励，转人工

### 4.11 运营数据

试营业要回答的问题都在这条漏斗上：

```
访问 → 粘贴查券 → 解析成功 → 有佣金 → 复制或跳转 → 下单 → 收货 → 过冻结 → 提现
```

所以从第一天就要记录每次查券，包括失败的。看板按平台、渠道、用户批次拆分：
- 查券成功率、查券到下单转化率
- 用户 7 日和 30 日复购
- 单用户净佣金、返利、奖励、毛利
- 邀请带来的用户占比和这批用户的毛利
- 退款率、无主订单率（衡量归因质量）
- 待收货、已失效金额统计，后台订单按平台、状态、绑定方式筛选（130）

查券记录保留期要定：同行只保 7 天（129），本方案归因要用，【建议】至少覆盖订单回补周期。用户中心展示未收货、冻结中、提现中、累计提现、可提现，加收益报表、我的订单、我的团队、在线客服、提现记录（030-01、036-01、011-02）。

和你们现在企微查券的数据对比，才知道小程序有没有更好。

## 5. 系统结构

### 5.1 模块

沿用基座现有模块：联盟接口加在 `ruoyi-union-sdk`，业务逻辑加在 `ruoyi-system`，接口加在 `ruoyi-admin`，定时任务加在 `ruoyi-quartz`。以下是按职责划分的业务包：

|---|---|
